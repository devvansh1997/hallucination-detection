\noindent\textbf{Purpose.} We are rerunning HARP's released code on our own generated data, so that
our comparison against their published numbers is like-for-like. While reading their code to build
the data adapter, we found one place where the released implementation does not match the setup
described in the paper. This document lists what we checked, with exact quotes and file/line
references, so it can be verified independently.

\medskip
\noindent\textbf{Summary.} The \emph{method} is implemented exactly as the paper describes --
detector architecture, token aggregation, optimiser, and correctness thresholds all match. The one
substantive difference is in \textbf{how the data is split into training and test sets}.

\section*{The one difference that matters, in plain terms}

\noindent\textbf{What is \emph{not} wrong.} The overall structure is right, and this should be stated
first to avoid overstating the finding. Questions are correctly labelled ``known'' or ``unknown''
according to the paper's definition; all unknown questions are correctly placed in the test set and
never used for training; and the 75/25 ratio is correctly applied only to the known group. There is
a genuine known/unknown separation.

\medskip
\noindent\textbf{What is wrong.} It is one level further down. Each question is answered ten times.
The paper says the 75/25 split within the known group is made \emph{over questions}. The code
instead pools that group's answers into a single list and splits \emph{that} at random.

The practical effect: a known question typically has around seven or eight of its ten answers in
training and the remaining two or three in the test set. Because the shuffle is random rather than a
clean per-question allocation, a known question keeps all ten answers on the training side only
about 5.6\% of the time ($0.75^{10}$) and almost never lands entirely in the test set. So roughly
\textbf{94\% of known questions contribute answers to both sides}, and for those the question is not
unseen at test time -- the detector was trained on other answers to it.

\medskip
\noindent The unknown questions are unaffected: none of their answers appear in training, so that
portion of the test set is genuinely unseen.

This matters for our project specifically, because our own analysis shows that a large share of
what these detectors appear to measure is \emph{which questions the model finds hard}, rather than
whether a particular answer is wrong. A split that puts the same question on both sides makes that
shortcut available to the detector.

\paragraph{How large is the effect likely to be?} It applies only to the ``25\% of known'' part of
the test set; the $\mathcal{X}_{unknown}$ questions are genuinely unseen. So the impact should scale
with how much of the test set comes from answerable questions. Using our own generations as a guide:
on Qwen/TruthfulQA roughly half the test answers would come from questions seen in training, whereas
on Qwen/NQ-Open only about 3\% would. If the effect is real, it should therefore inflate TruthfulQA
and TyDiQA-GP noticeably and NQ-Open barely.

\paragraph{Our own implementation follows the paper, not the code.} We split by question. This is
visible in our logs: for LLaMA/TruthfulQA we get 3{,}870 training answers (387 questions
$\times$ 10) and 4{,}300 test answers (430 questions $\times$ 10), summing to exactly 817 questions.
Every count is a clean multiple of ten. So our current comparison holds our method to a stricter
standard than their published numbers were produced under.

\section*{A separate note: the LLaMA model differs from ours}

This is \emph{not} a paper/code discrepancy -- the two agree -- but it affects our comparison. The
paper (\S5.1) evaluates ``Qwen-2.5-7B-Instruct and LLaMA-3.1-8B,'' and the code confirms it at
\texttt{main.py:20}, where the LLaMA entry points to \texttt{meta-llama/Llama-3.1-8B} -- the
\textbf{base} model, not the instruction-tuned one. Our generations used the Instruct variant,
\texttt{Meta-Llama-3.1-8B-Instruct}. The Qwen model matches exactly. Any like-for-like claim should therefore start with Qwen.

\section*{What we propose}

\begin{enumerate}
\item Run their code \textbf{exactly as released} on our generated data. We supply the data through
the cache files their pipeline already reads (\texttt{main.py:120--123}), so nothing in their method
is touched. If our numbers land close to their published ones, that confirms both the handoff and
the reading above.
\item Add a matching answer-level split option to \textbf{our} evaluator, so the two systems are
compared under identical conditions. This changes only our code, never theirs.
\item Treat this document as provisional until step 1 is done. The reading of the code is
straightforward, but a claim of this kind should rest on a reproduction rather than on a code
inspection alone.
\end{enumerate}

\noindent We would also note that this looks like a mismatch between the write-up and the released
implementation rather than anything deliberate: the paper's own formalism is precise, and the
method itself is implemented faithfully.
